# doit：進度檔管理與模板

依需要讀取對應章節：建立時讀「建立位置與命名」及適用模板；更新、接續或歸檔時讀「更新與接續規則」；首次使用 `.doit/` 或排除檢查失敗時讀「版控排除」。簡單修改的判定依 SKILL.md「定位與原則」。

## 建立位置與命名

在 Step1 規劃時，於實際執行任務的專案根目錄建立 `.doit/YYYY-MM-DD-任務簡稱.md`。日期使用使用者當地日期，任務簡稱採簡短且符合檔名規則的名稱，例如 `2026-10-13-calculator.md`。

- 每個任務使用一份進度檔；同一任務跨對話或跨 agent 接續時沿用原檔。
- 新專案在確認目標目錄後即可建立 `.doit/`，不必等待程式骨架完成。
- 建立前檢查現有檔案。同一任務沿用原檔；不同任務同名時加序號，不覆蓋既有紀錄。
- `.doit/` 是專案的任務紀錄目錄，與安裝 skill 的 `doit/` 目錄用途不同。
- 進度檔只保存必要摘要與證據位置，不保存密鑰或完整敏感日誌。

## 更新與接續規則

- 在計畫建立、Step 切換、子任務狀態變更、驗證完成、問題處理嘗試、需求變更及停止前更新檔案，不必逐次記錄工具呼叫。簡單修改可合併連續步驟的更新，但建立、交付及中斷前必須保存；失敗嘗試、需求變更與決策仍立即記錄。
- 原始目標保留不覆寫；使用者後續變更追加到「計畫變更」，並同步更新目前計畫與驗收項目。需求變更使受影響的驗證結果改為未驗證。
- 「目前步驟」與「下一步」保持最新；驗收勾選必須與驗證結果一致，只有「通過」或有理由的「不適用」才能打勾。
- 同一問題使用固定編號記錄嘗試次數，跨 Step、對話或 agent 接續仍沿用計數。達 3 次後，只有使用者明確要求繼續處理該問題，才能開始新一輪，並保留前一輪紀錄。
- 接續時先找出對應的進度檔：使用者指定檔案或任務時使用該檔；未指定時比對 `.doit/` 根目錄中未歸檔的進度檔，只有一份明確符合目前要求時直接沿用。有多份候選或無法確定時，列出各檔的任務名稱、狀態與更新時間，請使用者選擇，不自行猜測。
- 找到進度檔後先讀取，再核對實際檔案、工作區修改與必要驗證；不能只憑舊紀錄假定程式現況或測試仍有效。
- 等待回覆、暫停或遇到阻礙時保留原位。完成後更新狀態與時間，再移入 `.doit/archive/`；使用者明確取消時標示「已取消」後歸檔。歸檔時保留原檔名，目標同名已存在時加序號；歸檔不代表自動 commit。

## 版控排除

`.doit/` 是本機任務紀錄，預設不應進入版本控制。首次使用時執行以下檢查；後續沿用已確認的結果，發現排除失效或設定變更時重新檢查。

1. 專案不是 git 儲存庫時略過，進度檔記為「非 git 專案」。
2. 執行 `git check-ignore -q .doit/probe.md`；結束碼為 0 表示已被忽略，不需修改 ignore 檔，仍執行步驟 6。
3. 未被忽略時，若 `.doit/` 內任一進度檔（含 `archive/`）已記錄「使用者選擇不加入」，沿用該選擇，不再詢問。
4. 否則在 Step2 的集中提問中詢問使用者，提供三個選項：
   - **加入全局 gitignore（推薦）**：一般適用所有專案，且不修改專案檔案；仍以本專案檢查結果為準。
   - **加入專案 `.gitignore`**：只影響此專案，但會產生一筆專案檔案修改。
   - **不加入**。
5. 依使用者選擇執行，未經同意不修改任何 ignore 檔：
   - 全局：以 `git config --global core.excludesFile` 取得檔案路徑；未設定時使用 git 預設的全局 ignore 檔 `$XDG_CONFIG_HOME/git/ignore`，未設定 `XDG_CONFIG_HOME` 時為 `~/.config/git/ignore`（必要時建立目錄與檔案），不必另改 git 設定。
   - 專案：在專案根目錄 `.gitignore` 追加 `.doit/`；檔案不存在時建立。此修改列入交付說明。
   - 追加前確認檔案中沒有相同規則，保留原有內容，檔尾無換行時先補換行。完成後重跑步驟 2 確認生效。
   - 重查未通過時，記錄「尚未排除」與檢查結果，以 `git config --show-origin --get core.excludesFile` 及 `git check-ignore -v .doit/probe.md` 查明實際設定來源與忽略規則；專案設定可能覆寫全局設定。回 Step2 決定替代方式，不重複追加相同規則，不擅自修改其他設定或 ignore 檔。
6. 將結果記入進度檔「版控排除」欄位。若 `.doit/` 內已有檔案被 git 追蹤，加入 ignore 不會移除追蹤，告知使用者，不自動執行 `git rm --cached`。

## 精簡模板

僅適用於簡單修改。省略無關區塊，不必填寫空白子任務表或「無」；發生失敗、需求變更、決策或審查發現時，立即從完整模板補入對應區塊並保留紀錄。範圍擴大或需要分工時，在原檔補齊完整模板的相關欄位。

```markdown
# doit 進度檔：{任務名稱}

- 開始／更新時間：{使用者當地日期與時間，含時區；更新時保留開始時間}
- 狀態／目前步驟：規劃中／Step1
- 主 agent：{識別名稱或識別碼}
- 版控排除：{已排除（附來源）／尚未排除（附原因與下一步）／使用者選擇不加入／非 git 專案}
- 原始目標：{保留使用者原意，不覆寫；必要敏感內容遮蔽}
- [ ] A1：{成功條件、驗證方式、修改位置與處理方式}
- 驗證與證據：A1 未驗證；{執行後記錄操作、實際結果與證據位置，只有通過或有理由不適用才能打勾}
- 下一步：{具體動作；完成時記錄結果與結束時間，等待時寫明待確認事項}
```

## 完整模板

沒有失敗、變更或決策時填「無」，不要預填成功結果。

```markdown
# doit 進度檔：{任務名稱}

- 開始時間：{使用者當地日期與時間，含時區}
- 更新時間：{使用者當地日期與時間，含時區}
- 狀態：規劃中
- 主 agent：{識別名稱或識別碼}
- 分工方式：{主 agent 單獨執行／啟用 subagent，附簡短原因}
- 版控排除：{已排除（全局／專案）／尚未排除（附原因與下一步）／使用者選擇不加入／非 git 專案}

## 原始目標（保留原意，不覆寫）
{使用者最初要求；必要敏感內容遮蔽}

## 目標與目前計畫
- 交付物：{預期產出}
- 範圍與限制：{本次需完成的範圍及限制}
- 影響範圍：{相關檔案或模組；新專案則列預計建立項目}
- 執行方案：{最小完整方案}

## 驗收項目
只有結果為「通過」或有理由的「不適用」才能打勾。
- [ ] A1：{可觀察的成功條件及驗證方式}（來源：{對應的使用者原話}）

改善建議（非必要範圍）：無。

Step1 — Understand & Plan

## 下一步

## 驗證紀錄
結果使用：通過、失敗、未驗證、不適用（附理由）。驗證後修改了受測內容時，將受影響結果改為未驗證並重新驗證。

| 驗收項目 | 指令或操作 | 結果 | 證據位置 |
|---|---|---|---|
| A1 | {驗證方式} | 未驗證 | — |

## 問題與失敗嘗試
無。發生問題時記錄：問題編號、關聯驗收項目或子任務、判定的根因、當前處理者、共用嘗試次數（1/3～3/3）、方法、結果及下一步。保留每次嘗試紀錄，改派 agent 不重設計數。

## 審查紀錄
尚未執行。執行後記錄審查者、審查範圍，以及每項發現的編號、嚴重度（阻擋性／非阻擋性）、證據、主 agent 判定與理由、修正及確認關閉的結果；未安排獨立審查時記錄原因。

## 關鍵決策與待確認事項
無。

## 計畫變更
無。需求調整時追加時間、變更內容、來源及對驗收的影響。

## 結束或停止紀錄
尚未結束。結束時記錄時間、狀態、原因、未完成事項及必要後續工作。
```

任務狀態使用：規劃中、進行中、等待使用者、已停止、已完成、已取消。子任務狀態使用：待開始、進行中、待驗證、已完成、受阻、已取消。
