# doit：進度檔管理與模板

依需要讀取對應章節：建立時讀「建立」、適用模板與「版控排除」；更新讀「更新」；處理問題時讀「問題計數」；接續讀「接續」與「版控排除」；結束讀「歸檔」。S／M／L 的判定依 SKILL.md「任務分級」。

## 建立

在 Step2 規劃時，於實際執行任務的專案根目錄建立 `.doit/YYYY-MM-DD-任務簡稱/progress.md`，例如 `.doit/2026-10-13-calculator/progress.md`。任務簡稱使用英文小寫與連字號，避免中文路徑在終端機與 git 中出現編碼問題。

- 日期與時間使用使用者當地時間。用 shell 取得，不要自行推測：bash 用 `date '+%Y-%m-%d %H:%M %z'`，PowerShell 用 `Get-Date -Format 'yyyy-MM-dd HH:mm zzz'`。
- **選擇模板依任務等級與結構，不單獨依風險**：S／M 預設用精簡模板；L、需要實作分工，或預計跨多次對話的任務用完整模板。只安排獨立審查（含高風險的 M）不強制改用完整模板，在精簡模板補入「審查紀錄」；必要驗證與審查紀錄不得省略。
- 每個任務一個資料夾，內含一份 `progress.md`。不同任務同名時在資料夾名稱加序號（例如 `2026-10-13-calculator-2/`），不覆蓋既有紀錄。
- 任務產生的 log、截圖、驗證輸出與其他輔助檔案存放於該任務資料夾；有需要才建立 `logs/` 等子目錄。專案交付物仍放在專案原有位置。
- 在進度檔中以相對於 `progress.md` 的路徑引用附件（例如 `logs/test.log`），讓歸檔後的證據連結仍有效。
- 新專案在確認目標目錄後即可建立 `.doit/`，不必等待程式骨架完成。
- `.doit/` 是專案的任務紀錄目錄，與安裝 skill 的 `doit/` 目錄用途不同。
- 只保存必要摘要與證據位置，不保存密鑰或完整敏感日誌；原始目標中的敏感內容要遮蔽。

## 更新

- **所有模板共用**：建立時、各階段 Markdown 回報前，以及等待使用者、受阻、停止或其他可預見的中斷前更新。同步任務狀態、更新時間、「目前步驟」與「下一步」，使檔案與對話一致；目前步驟記錄回報當下的 Step，下一步寫即將執行或返回的 Step 與具體動作。尚未建檔時先在對話回報，建檔後補入先前結果。對話格式依 SKILL.md「階段 Markdown 回報」，檔案只保存必要摘要與證據，不必逐字複製報告或逐次記錄工具呼叫。
- **完整模板的任務**：在計畫建立、Step 切換、子任務狀態變更、驗證完成、問題處理嘗試、需求變更及停止前更新，不必逐次記錄工具呼叫。
- **精簡模板的任務**：
  - 寫入時機同上述共用規則，沿用精簡模板，不因每階段回報就擴充為完整模板。
  - Step4 完成時在「要做的任務」列出修改的檔案，將已實作的工作項目標示為「待驗證」；對應驗收結果仍為「未驗證」，讓無預警中斷後仍能接續。
  - 修正前的失敗證據、失敗嘗試、需求變更、決策或審查發現發生時立即補記。需要的區塊（例如「審查紀錄」「關鍵決策與待確認事項」）直接從完整模板補入，沿用相同標題，不自創區塊。
  - 升為 L、需要實作分工或預計跨多次對話時，在同一份檔案補齊完整模板的相關欄位。
- 等級變更時更新等級與理由，並在「計畫變更」保留變更前後等級及原因，不另開進度檔。
- 原始目標保留不覆寫；使用者後續變更追加到「計畫變更」，並同步更新目前計畫與驗收項目。需求變更使受影響的驗證結果改為未驗證。
- 每次依上述時機寫入進度檔時，同步更新置頂「目前進度」中的狀態、目前步驟、正在處理、下一步與需要使用者處理的事項；只有「通過」或有理由的「不適用」的驗收項目才能打勾。

## 問題計數

SKILL.md「失敗與重試規則」的 3 次上限依下列方式計數：

- **同一問題**：根因相同就是同一問題，不論換了寫法、方法、Step 或負責的 agent；無法判斷是否為同一根因時，視為同一問題。確定根因不同的新失敗另開問題編號。
- **一次嘗試**：採取一個處理方案並驗證結果，第一次處理也算；最初發現問題的檢查不算。主 agent 與所有 subagent 共用計數。
- **機械性錯誤**：拼字、漏 import、格式等一次修正即通過時不計；修正後仍失敗或再次出現則開始計數。
- **環境問題**：終端機編碼、缺少工具等與修改無關的問題不計入上限；改用可行方式完成驗證，只有影響結果時才寫入交付的「限制」。
- 同一問題使用固定編號記錄嘗試次數，跨 Step、對話或 agent 接續仍沿用計數。第 3 次仍失敗時，只有使用者明確要求繼續處理該問題，才能開始新一輪，並保留前一輪紀錄。第 3 次成功則記錄已解決，可繼續或接續其餘工作，不因次數達 3 而要求重新授權。

## 接續

- 使用者指定進度檔、任務資料夾或任務名稱時，使用對應的進度檔；資料夾路徑對應其內的 `progress.md`。沒有指定（含只說「繼續」）時，查找 `.doit/*/progress.md`（排除 `.doit/archive/`）及舊版 `.doit/*.md`：只有一份未歸檔進度檔就直接沿用；有多份，或有參數但無法確定對應哪一份時，列出各檔的任務名稱、狀態與更新時間，請使用者選擇，不自行猜測。
- 舊版單檔紀錄接續時保留原位，不自動搬移；新任務使用資料夾格式。
- 找到進度檔後先讀取，再核對實際檔案、工作區修改與必要驗證；舊紀錄可能已過時，不能只憑它假定程式現況或測試仍有效。
- 舊紀錄的「通過」只代表當時的結果；Step5 仍要在最終版本上重新驗證受影響的項目。
- 接續舊五步驟紀錄時，依步驟名稱與實際完成內容對照新流程：舊 Step1 拆為新 Step1／Step2，舊 Step2／Step3／Step4 分別對應新 Step3／Step4／Step5，舊 Step5 拆為新 Step6／Step7。更新目前步驟與下一步，不改寫歷史紀錄；缺少任務等級時依現況補判並記錄理由。
- 舊檔缺少目前模板的區塊時不必一次補齊，用到時再加入。更新舊版面時，將目前步驟與下一步移到置頂「目前進度」，「子任務」改排為「要做的任務」，「目標與目前計畫」改為「方案與範圍」；保留既有任務編號、證據與歷史紀錄，不因換版重新計數。

## 歸檔

- 全部必要驗收項目通過（或有理由不適用）、完成 Step6 審查且阻擋性發現已解決後，更新狀態與時間，將整個任務資料夾（含 `progress.md` 與附件）移入 `.doit/archive/`，例如 `.doit/archive/2026-10-13-calculator/progress.md`。使用者明確取消時標示「已取消」後歸檔。
- 等待回覆、暫停、停止或遇到阻礙時保留原位，記錄阻礙與下一步。
- 歸檔時保留原資料夾名稱，目標同名已存在時在資料夾名稱加序號，不覆蓋或合併。舊版單檔紀錄仍以原檔名移入 `.doit/archive/`，同名時加序號。歸檔不代表自動 commit。
- 交付時寫進度檔的最終位置；已歸檔就寫 archive 中的路徑。

## 版控排除

`.doit/` 是本機任務紀錄，不應進入版本控制。建立或接續任務時：

1. 確保 `.doit/.gitignore` 存在，新建時內容為一行 `*`（檔尾換行），排除進度檔、附件、archive 及 `.gitignore` 本身。已有檔案則保留內容，缺少 `*` 時在檔尾補入，檔尾無換行時先補換行，不重複追加。
2. 專案不是 git 儲存庫時，建立檔案後略過 git 檢查。
3. 在專案根目錄執行 `git check-ignore -q .doit/.gitignore` 與 `git check-ignore -q .doit/probe/progress.md`，兩者結束碼皆為 0 才確認排除生效；另用 `git ls-files -- .doit/` 檢查是否已有受追蹤檔案。
4. 無法寫入、排除未生效，或 `.doit/` 內已有檔案被 git 追蹤時，記入進度檔並在交付的「限制」中告知使用者。排除成功時不必寫入進度檔，首次設定時在交付提一句即可。不自行修改其他 ignore 檔或 git 設定，也不執行 `git rm --cached`；已受追蹤的檔案不會因新增 `.gitignore` 而停止追蹤。

## 模板填寫規則

- 兩份模板都依「目前進度 → 要做的任務 → 驗收項目 → 驗證紀錄 → 原始目標 → 方案與範圍 → 任務資料」排列，讓使用者先看到現在要做什麼，再查背景與證據。
- 工作項目使用 T1、T2…，驗收項目使用 A1、A2…。每個工作項目以動作命名，標題直接附狀態；Step2 的規劃項目寫入「要做的任務」，不是只列 SOP 的七個步驟。
- 工作項目狀態使用：待開始、進行中、待驗證、已完成、受阻、已取消。實作完成先標「待驗證」，主 agent 核對相關驗證符合條件後才能標「已完成」；整體任務完成仍須符合 SKILL.md Step6、Step7。
- 驗收項目只寫成功條件與需求來源；預定驗證方式及實際證據集中在「驗證紀錄」，工作項目的「驗證」可直接引用對應 A 編號，避免重複長段內容。驗收結果使用：通過、失敗、未驗證、不適用（附理由）；驗證後修改了受測內容，受影響結果改為未驗證並重新驗證。
- 任務狀態使用：規劃中、進行中、等待使用者、已停止、已完成、已取消。正在處理欄位標示 T 編號與具體動作，交付時改寫實際結束情況，不預填成功。
- 問題、審查、決策、變更與結束紀錄放在任務資料之後，沿用下方完整模板的區塊名稱與必要資訊。

## 精簡模板

適用於不需實作分工且未預計跨多次對話的 S／M 任務（見「建立」）。省略無關的欄位，不為了填滿欄位而寫「無」。

```markdown
# 任務：{任務名稱}

## 目前進度

- 狀態：{目前狀態}
- 目前步驟：{StepN／7 名稱}
- 正在處理：{T 編號與具體動作}
- 下一步：{即將執行或返回的 Step 與具體動作}
- 需要你處理：{必要問題或決定；沒有則寫「無」}

## 要做的任務

### T1 {具體工作}｜待開始

- 工作：{要做什麼及原因}
- 位置：{修改的檔案或模組}
- 驗證：{對應 A 編號的驗證方式；必要的額外檢查}
- 對應驗收：A1

## 驗收項目

- [ ] A1：{可觀察的成功條件；對應的使用者需求}

## 驗證紀錄

### A1｜未驗證

- 方式：{預定指令或操作}
- 證據：尚未執行。

## 原始目標

{保留使用者原意，不覆寫；必要敏感內容遮蔽}

## 方案與範圍

- 交付物：{預期產出}
- 執行順序：{T 編號的先後順序；只有一項時可省略}
- 範圍限制：{本次範圍與必須維持的行為}

## 任務資料

- 任務等級：{S／M；判定理由}
- 分工方式：主 agent 單獨執行
- 開始時間：{使用者當地日期與時間，含時區}
- 更新時間：{使用者當地日期與時間，含時區}
```

填寫完成的範例（使用者要求「把頁尾的版權年份改成 2026」）：

```markdown
# 任務：頁尾版權年份

## 目前進度

- 狀態：已完成
- 目前步驟：Step7／7 Deliver
- 正在處理：已結束，成果已交付。
- 下一步：無。
- 需要你處理：無。

## 要做的任務

### T1 更新頁尾版權年份｜已完成

- 工作：將年份常數改為 2026，符合使用者要求。
- 位置：src/components/Footer.tsx
- 驗證：依 A1 的讀回檢查與既有測試。
- 對應驗收：A1

## 驗收項目

- [x] A1：頁尾顯示「© 2026」。（來源：把頁尾的版權年份改成 2026）

## 驗證紀錄

### A1｜通過

- 方式：讀回 Footer.tsx 並執行 `npm test -- Footer`。
- 證據：第 12 行年份為 2026；Footer 測試 3/3 通過。

## 原始目標

把頁尾的版權年份改成 2026。

## 方案與範圍

- 交付物：顯示 2026 年的頁尾。
- 範圍限制：只修改既有年份常數，不改變行為與介面。

## 任務資料

- 任務等級：S；僅更新版權文字。
- 分工方式：主 agent 單獨執行
- 開始時間：2026-10-15 14:02 +0800
- 更新時間：2026-10-15 14:06 +0800

## 審查紀錄

- 審查者：主 agent 自我檢查；不涉及高風險或跨模組修改。
- 結果：對照原始需求與最終修改，未發現漏改、多做或阻擋性問題；驗證證據對應最終版本。

## 結束或停止紀錄

- 時間：2026-10-15 14:06 +0800
- 狀態：已完成；A1 通過且完成自我檢查，已交付並歸檔。
- 未完成事項與後續工作：無。
```

## 完整模板

適用於 L、需要實作分工或預計跨多次對話的任務。沒有失敗、變更或決策時填「無」，不要預填成功結果。

```markdown
# 任務：{任務名稱}

## 目前進度

- 狀態：規劃中
- 目前步驟：Step2／7 Plan
- 正在處理：{T 編號與具體動作；尚在規劃時寫明規劃內容}
- 下一步：{即將執行或返回的 Step 與具體動作}
- 需要你處理：{必要問題或決定；沒有則寫「無」}

## 要做的任務

### T1 {具體工作}｜待開始

- 工作：{要做什麼及原因}
- 位置：{可修改的檔案或模組}
- 驗證：{對應 A 編號的驗證方式；必要的額外檢查}
- 對應驗收：A1
- 負責者：{主 agent 或 subagent 的名稱／用途}
- 依賴：{前置 T 編號及必要產出；沒有則寫「無」}
- 整合安排：{接合位置、順序及整合驗證；不需要時省略}

## 驗收項目

- [ ] A1：{可觀察的成功條件}（來源：{對應的使用者原話}）

改善建議（非必要範圍）：無。

## 驗證紀錄

### A1｜未驗證

- 方式：{預定指令或操作；執行後寫實際方式}
- 證據：尚未執行。{執行後記錄實際結果及證據位置}
- 原因與限制：{失敗、未驗證或不適用時的原因；通過且無限制時省略}

## 原始目標

{使用者最初要求；保留原意，不覆寫；必要敏感內容遮蔽}

## 方案與範圍

- 交付物：{預期產出}
- 執行順序：{T 編號的先後順序與可平行項目}
- 範圍限制：{本次範圍、排除事項與必須維持的行為}
- 影響範圍：{相關介面、模組及相容性影響；新專案則列必要結構與啟動方式}

## 任務資料

- 任務等級：{S／M／L；判定理由}
- 分工方式：{主 agent 單獨執行／啟用 subagent，附簡短原因}
- 開始時間：{使用者當地日期與時間，含時區}
- 更新時間：{使用者當地日期與時間，含時區}

## 問題與失敗嘗試
無。發生問題時記錄：問題編號、關聯驗收項目或子任務、判定的根因、當前處理者、共用嘗試次數（1/3～3/3）、方法、結果及下一步。保留每次嘗試紀錄，改派 agent 不重設計數。

## 審查紀錄
尚未執行。執行後記錄審查者、審查範圍，以及每項發現的編號、嚴重度（阻擋性／非阻擋性）、證據、主 agent 判定與理由、修正及確認關閉的結果；未安排獨立審查時記錄原因。

## 關鍵決策與待確認事項
無。

## 計畫變更
無。需求調整時追加時間、變更內容、來源及對驗收的影響。

## 結束或停止紀錄
尚未結束。結束時記錄時間、狀態、原因、未完成事項及必要後續工作。
```
