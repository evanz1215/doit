# doit：進度檔管理與模板

依需要讀取對應章節：建立時讀「建立」與適用模板，首次在該專案建立 `.doit/` 時再讀「版控排除」；更新讀「更新」；處理問題時讀「問題計數」；接續讀「接續」；結束讀「歸檔」。S／M／L 的判定依 SKILL.md「任務分級」。

## 建立

在 Step2 規劃時，於實際執行任務的專案根目錄建立 `.doit/YYYY-MM-DD-任務簡稱.md`，例如 `2026-10-13-calculator.md`。任務簡稱使用英文小寫與連字號，避免中文檔名在終端機與 git 中出現編碼問題。

- 日期與時間使用使用者當地時間。用 shell 取得，不要自行推測：bash 用 `date '+%Y-%m-%d %H:%M %z'`，PowerShell 用 `Get-Date -Format 'yyyy-MM-dd HH:mm zzz'`。
- **選擇模板依任務等級與結構，不單獨依風險**：S／M 預設用精簡模板；L、需要實作分工，或預計跨多次對話的任務用完整模板。只安排獨立審查（含高風險的 M）不強制改用完整模板，在精簡模板補入「審查紀錄」；必要驗證與審查紀錄不得省略。
- 每個任務一份進度檔。不同任務同名時加序號，不覆蓋既有紀錄。
- 新專案在確認目標目錄後即可建立 `.doit/`，不必等待程式骨架完成。
- `.doit/` 是專案的任務紀錄目錄，與安裝 skill 的 `doit/` 目錄用途不同。
- 只保存必要摘要與證據位置，不保存密鑰或完整敏感日誌；原始目標中的敏感內容要遮蔽。

## 更新

- **完整模板的任務**：在計畫建立、Step 切換、子任務狀態變更、驗證完成、問題處理嘗試、需求變更及停止前更新，不必逐次記錄工具呼叫。
- **精簡模板的任務**：
  - 寫入時機：建立時、Step4 實作完成進入 Step5 前、交付時，以及等待使用者、停止或其他可預見的中斷前。
  - Step4 完成時列出修改的檔案，並將驗收項目標示為「待驗證」，讓無預警中斷後仍能接續。
  - 修正前的失敗證據、失敗嘗試、需求變更、決策或審查發現發生時立即補記。需要的區塊（例如「審查紀錄」「關鍵決策與待確認事項」）直接從完整模板補入，沿用相同標題，不自創區塊。
  - 升為 L、需要實作分工或預計跨多次對話時，在同一份檔案補齊完整模板的相關欄位。
- 等級變更時更新等級與理由，並在「計畫變更」保留變更前後等級及原因，不另開進度檔。
- 原始目標保留不覆寫；使用者後續變更追加到「計畫變更」，並同步更新目前計畫與驗收項目。需求變更使受影響的驗證結果改為未驗證。
- 每次依上述時機寫入進度檔時，同步更新「目前步驟」與「下一步」；只有「通過」或有理由的「不適用」才能打勾。

## 問題計數

SKILL.md「失敗與重試規則」的 3 次上限依下列方式計數：

- **同一問題**：根因相同就是同一問題，不論換了寫法、方法、Step 或負責的 agent；無法判斷是否為同一根因時，視為同一問題。確定根因不同的新失敗另開問題編號。
- **一次嘗試**：採取一個處理方案並驗證結果，第一次處理也算；最初發現問題的檢查不算。主 agent 與所有 subagent 共用計數。
- **機械性錯誤**：拼字、漏 import、格式等一次修正即通過時不計；修正後仍失敗或再次出現則開始計數。
- **環境問題**：終端機編碼、缺少工具等與修改無關的問題不計入上限；改用可行方式完成驗證，只有影響結果時才寫入交付的「限制」。
- 同一問題使用固定編號記錄嘗試次數，跨 Step、對話或 agent 接續仍沿用計數。第 3 次仍失敗時，只有使用者明確要求繼續處理該問題，才能開始新一輪，並保留前一輪紀錄。第 3 次成功則記錄已解決，可繼續或接續其餘工作，不因次數達 3 而要求重新授權。

## 接續

- 使用者指定檔案或任務時使用該檔。沒有指定（含只說「繼續」）時：`.doit/` 根目錄只有一份未歸檔進度檔就直接沿用；有多份，或有參數但無法確定對應哪一份時，列出各檔的任務名稱、狀態與更新時間，請使用者選擇，不自行猜測。
- 找到進度檔後先讀取，再核對實際檔案、工作區修改與必要驗證；舊紀錄可能已過時，不能只憑它假定程式現況或測試仍有效。
- 舊紀錄的「通過」只代表當時的結果；Step5 仍要在最終版本上重新驗證受影響的項目。
- 接續舊五步驟紀錄時，依步驟名稱與實際完成內容對照新流程：舊 Step1 拆為新 Step1／Step2，舊 Step2／Step3／Step4 分別對應新 Step3／Step4／Step5，舊 Step5 拆為新 Step6／Step7。更新目前步驟與下一步，不改寫歷史紀錄；缺少任務等級時依現況補判並記錄理由。
- 舊檔缺少目前模板的區塊時不必一次補齊，用到時再加入。

## 歸檔

- 全部必要驗收項目通過（或有理由不適用）、完成 Step6 審查且阻擋性發現已解決後，更新狀態與時間，將檔案移入 `.doit/archive/`。使用者明確取消時標示「已取消」後歸檔。
- 等待回覆、暫停、停止或遇到阻礙時保留原位，記錄阻礙與下一步。
- 歸檔時保留原檔名，目標同名已存在時加序號。歸檔不代表自動 commit。
- 交付時寫進度檔的最終位置；已歸檔就寫 archive 中的路徑。

## 版控排除

`.doit/` 是本機任務紀錄，不應進入版本控制。首次在專案建立 `.doit/` 時：

1. 專案不是 git 儲存庫時略過。
2. 執行 `git check-ignore -q .doit/probe.md`；結束碼為 0 表示已被忽略，不需修改。
3. 否則將 `.doit/` 追加到 `git rev-parse --git-path info/exclude` 回傳的檔案：不存在就建立，已有相同規則就不重複追加，檔尾無換行時先補換行。完成後重跑步驟 2 確認生效。
   - 使用 `git rev-parse` 取得路徑，是因為在 worktree 或 submodule 中 `.git` 可能是檔案而非目錄。
   - 此設定不會被 commit，但 linked worktree 會共用，因此也會影響同一儲存庫的其他 worktree。依本 skill 將 `.doit/` 留在本機的規則直接加入，不另行詢問。
4. 仍未生效，或 `.doit/` 內已有檔案被 git 追蹤時，記入進度檔並在交付的「限制」中告知使用者。排除成功時不必寫入進度檔，交付時提一句即可。不自行修改其他 ignore 檔或 git 設定，也不執行 `git rm --cached`。

## 精簡模板

適用於不需實作分工且未預計跨多次對話的 S／M 任務（見「建立」）。省略無關的欄位，不為了填滿欄位而寫「無」。

```markdown
# doit 進度檔：{任務名稱}

- 時間：{開始時間}；更新 {最後更新時間}
- 狀態／目前步驟：{目前狀態}／{目前 Step}
- 任務等級：{S／M；判定理由}
- 原始目標：{保留使用者原意，不覆寫}
- 方案：{必要修改與執行方式}
- [ ] A1：{成功條件；修改位置；驗證方式}
- 驗證與證據：A1 未驗證
- 下一步：{具體動作；等待時寫明待確認事項}
```

填寫完成的範例（使用者要求「把頁尾的版權年份改成 2026」）：

```markdown
# doit 進度檔：頁尾版權年份

- 時間：2026-10-15 14:02 +0800；更新 2026-10-15 14:06 +0800
- 狀態／目前步驟：已完成／Step7
- 任務等級：S；僅更新版權文字，不改變行為與介面
- 原始目標：把頁尾的版權年份改成 2026
- 方案：修改既有 Footer 元件中的年份常數
- [x] A1：頁尾顯示「© 2026」；修改 src/components/Footer.tsx 的年份常數；驗證方式為讀回檔案並執行既有 Footer 測試
- 驗證與證據：A1 通過；`npm test -- Footer` 3/3 通過，讀回 Footer.tsx 第 12 行確認為 2026
- 下一步：無，已交付
```

## 完整模板

適用於 L、需要實作分工或預計跨多次對話的任務。沒有失敗、變更或決策時填「無」，不要預填成功結果。

```markdown
# doit 進度檔：{任務名稱}

- 開始時間：{使用者當地日期與時間，含時區}
- 更新時間：{使用者當地日期與時間，含時區}
- 狀態：規劃中
- 任務等級：{S／M／L；判定理由}
- 分工方式：{主 agent 單獨執行／啟用 subagent，附簡短原因}

## 原始目標（保留原意，不覆寫）
{使用者最初要求；必要敏感內容遮蔽}

## 目標與目前計畫
- 交付物：{預期產出}
- 範圍與限制：{本次需完成的範圍及限制}
- 影響範圍：{相關檔案或模組；新專案則列預計建立項目}
- 執行方案：{最小完整方案}

## 驗收項目
只有結果為「通過」或有理由的「不適用」才能打勾。
- [ ] A1：{可觀察的成功條件及驗證方式}（來源：{對應的使用者原話}）

改善建議（非必要範圍）：無。

## 子任務
| 編號 | 子任務 | 負責者 | 修改範圍 | 依賴 | 驗收項目 | 狀態 |
|---|---|---|---|---|---|---|
| 1 | {工作項目} | {主 agent，或 subagent 的名稱／用途} | {檔案或模組} | 無 | A1 | 待開始 |

## 目前步驟
Step2 — Plan

## 下一步
{下一個具體動作；等待時寫明需要的資訊}

## 驗證紀錄
結果使用：通過、失敗、未驗證、不適用（附理由）。驗證後修改了受測內容時，將受影響結果改為未驗證並重新驗證。

| 驗收項目 | 指令或操作 | 結果 | 證據位置 |
|---|---|---|---|
| A1 | {驗證方式} | 未驗證 | — |

## 問題與失敗嘗試
無。發生問題時記錄：問題編號、關聯驗收項目或子任務、判定的根因、當前處理者、共用嘗試次數（1/3～3/3）、方法、結果及下一步。保留每次嘗試紀錄，改派 agent 不重設計數。

## 審查紀錄
尚未執行。執行後記錄審查者、審查範圍，以及每項發現的編號、嚴重度（阻擋性／非阻擋性）、證據、主 agent 判定與理由、修正及確認關閉的結果；未安排獨立審查時記錄原因。

## 關鍵決策與待確認事項
無。

## 計畫變更
無。需求調整時追加時間、變更內容、來源及對驗收的影響。

## 結束或停止紀錄
尚未結束。結束時記錄時間、狀態、原因、未完成事項及必要後續工作。
```

任務狀態使用：規劃中、進行中、等待使用者、已停止、已完成、已取消。子任務狀態使用：待開始、進行中、待驗證、已完成、受阻、已取消。
